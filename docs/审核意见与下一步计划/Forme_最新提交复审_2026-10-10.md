# 1. 总体结论

本次提交已经不是普通的小功能补丁，而是一次较大范围的功能扩张。Forme 已从早期桌宠原型进入 **0.5.x 玩法系统阶段**，成长、星星、家具、任务、收藏、成就、纸船、本地动作规则、AI 动作协议、多模型和场景互动等系统已经基本形成。

当前主要问题已经从“功能太少”转变为两类：

1. **工程稳定性仍有阻塞项**：GitHub Actions 当前仍失败，不能作为正式发布状态；
2. **系统数量已经不少，但可消费内容量偏少**：任务、家具、发现物、成就、玩具等内容很快会被玩家体验完。

因此当前不建议继续快速新增大型独立系统。优先级应调整为：

```text
先让 main 变绿
    ↓
补稳定性边界和正式性能测试
    ↓
扩充现有玩法内容
    ↓
再进入 0.6 发布阶段
```

综合判断：**当前暂不建议正式发布 0.5.7**。

# 3. P0 问题

## 3.1 P0-01：`ActionRules.UpgradeDefaults()` 历史规则升级识别不完整

当前升级逻辑主要依赖：

```text
Serialize() 后整份 JSON 字符串比较
```

现有代码能够识别两类历史默认规则：

1. 缺少 `lap1/lap2` 的旧默认规则；
2. 缺少 `lap1/lap2`，同时旋转动作只包含旧短语“转圈舞”的更早默认规则。

但当前测试构造的历史状态是：

```text
已经存在 lap1/lap2
+
spin 仍然只有“转圈舞”
```

该状态没有被 `UpgradeDefaults()` 识别，因此规则不会升级。

随后：

```csharp
old.UpgradeDefaults().Match("转一圈看看")
```

返回 `null`，测试继续使用：

```csharp
![0]
```

最终触发 `NullReferenceException`。

### 短期修复建议

增加第三种官方历史默认快照：

```csharp
var spinPrevious = current with
{
    Rules = current.Rules.Select(r =>
        r.Commands.Length == 1 &&
        r.Commands[0] == new CompanionCommand("dance", "spin")
            ? r with { Phrases = ["转圈舞"] }
            : r
    ).ToArray()
};

return Serialize() == previous.Serialize()
    || Serialize() == earlier.Serialize()
    || Serialize() == spinPrevious.Serialize()
        ? current
        : this;
```

### 中期优化建议

不要继续把“整个规则 JSON 是否完全相等”作为版本迁移条件。

建议增加：

```text
SchemaVersion
BuiltinRevision
```

职责拆分为：

```text
SchemaVersion
    → JSON / 数据结构格式版本

BuiltinRevision
    → 官方默认动作规则版本
```

这样后续增加默认短语、动作或规则时，不需要维护越来越多的完整 JSON 快照。

## 3.2 P0-02：修完测试后，CI 仍然会在 crash-test 阶段失败

上一版提交的 GitHub Actions 已经证明：

```text
build.ps1 -Test -Package
```

本身可以成功完成。

但后面的：

```text
Verify fatal error exits with private diagnostics
```

存在路径错误。

当前 `windows.yml` 直接调用：

```powershell
./.tools/dotnet/dotnet.exe
```

以及：

```powershell
Start-Process .tools/dotnet/dotnet.exe
```

GitHub Hosted Runner 并没有该本地路径。

`actions/setup-dotnet` 提供的是系统 `dotnet`。

项目自己的 `build.ps1` 已经实现了正确逻辑：

```powershell
$formeSdk = Join-Path $formeRoot '.tools/dotnet/dotnet.exe'

if (-not (Test-Path -LiteralPath $formeSdk)) {
    $formeSdk = (Get-Command dotnet).Source
}
```

### 建议

CI 也采用同样策略，例如：

```powershell
$dotnet = (Get-Command dotnet).Source

& $dotnet build src/Forme.App/Forme.App.csproj `
    -c Release `
    --no-restore `
    '-p:FormeDevelopmentTools=true'

if ($LASTEXITCODE -ne 0) {
    throw 'Development test host build failed'
}
```

启动 crash-test 时同样使用：

```powershell
Start-Process $dotnet ...
```

该问题建议与 `ActionRules` 修复放在下一提交一起处理。

# 4. P1 稳定性问题

## 4.1 `LifeRules` 对部分家具布局增加防御

当前 `LivingWorld.Validate()` 并不要求默认家具必须全部存在，这是合理的，因为后续用户可能：

- 收纳家具；
- 导入旧布局；
- 使用自定义摆放；
- 后续扩展更多家具类型。

但 `LifeRules` 内部仍存在：

```csharp
world.Items.First(x => x.Kind == kind)
```

这种假设目标家具一定存在的实现。

当前 8 条规则大多因为条件和目标家具刚好对应，因此通常不会立即出错，但这属于脆弱接口。

未来新增事件时，如果：

```text
判断条件使用 A/B 家具
但最终 target 使用 C 家具
```

且 C 不存在，就可能直接触发：

```text
InvalidOperationException
```

### 建议

将目标查找改为：

```csharp
var target = world.Items.FirstOrDefault(x => x.Kind == kind);
if (target is null)
    return;
```

并补以下测试：

```text
EmptyFurnitureWorldDoesNotThrow
MissingCushionDoesNotThrow
MissingBookDoesNotThrow
MissingLampDoesNotThrow
ImportedPartialLayoutDoesNotThrow
```

# 7. 本地动作规则评价

这是当前版本比较值得保留的一项设计。

明确、确定性的短句，例如：

```text
走两步
跑几步
回来
别动
转一圈
睡觉
去书架旁
玩小球
玩纸船
打开灯
关灯
```

优先匹配本地规则：

```text
本地动作
↓
不调用 AI
↓
不消耗 Token
↓
动作仍然走权限和白名单
```

本地动作消息使用：

```text
status = local
```

并从 AI 历史中排除。

这能同时解决：

- AI 成本；
- 延迟；
- AI 误判；
- 上下文污染；
- 简单指令体验不稳定。

后续建议继续扩大本地确定性动作覆盖，而不是所有交互都交给 AI。
